# arch-refactor

Work from the diagnosed causes and the design, not from the score. CodeScene is not run in this phase. The baseline came from `arch-diagnose`, and the comparison belongs to `arch-verify`.

## Before the first edit

- There is a diagnosis (and a design above the Local level). If not, run `arch-diagnose` first.
- Tests that pin the behaviour are green. Where none exist, add a characterization test at the module's interface first.
- **This repository**: tests run through Bazel only (`bazel test //...`, `--config=lint`, `--config=fmt`). Generated scaffolds and derived files are produced by the generator, never edited by hand: a change to a planner that alters generated bytes is a new profile version, not a refactor (see `docs/generation-boundary.md`).

## Loop: one cause at a time

1. Make a structural step that moves one diagnosed cause toward its design: introduce the concept, move the behaviour onto it, delete the old path. When the design includes a missing infrastructure capability, add the capability first, then delete the workaround it made necessary.
2. Run the tests. If they are red, fix the step or revert it; never refactor further while red.
3. Check the step against "Gaming" in `../arch-diagnose/references/smells.md` and against the design. A placeholder name, a parameter bag, logic pushed into a caller, or a split that only makes sense read together is reverted and replaced by the honest move. If no honest fix exists, leave the finding open.
4. If the design turns out to be wrong, revise the design (and re-diagnose if the causes changed) before continuing. Do not drift into an unplanned shape.

## Stop

**Implementation is complete** when the design's acceptance criteria hold, the result is coherent, and the tests are green. Then hand over to `arch-verify`. Do not declare success yourself, and do not run CodeScene to decide whether you are done.

Report every diagnosed cause as resolved or as open debt with its reason. List debt you found outside the agreed objective separately; do not fix it silently.

## Never

- Edit CodeScene rules or thresholds, or add suppression comments. These change the measurement, not the code, and are the user's decision.
- Change behaviour, or change a published external contract, without the design saying so (see the escalation list in `../arch/references/impact-levels.md`).
- Work around a missing capability in shared infrastructure when the design calls for adding it.
- Move complexity into callers, tests, configuration or decorators.
