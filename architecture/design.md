Architect: the repository owner. Date: 2026-11-13. Knowledge base: `architecture-knowledge/` (rulings first).
Scope: audit decisions Q1 and Q3, which fix the cause of F8, F9 and F10, and of part of F14 (`architecture/audit.md`). The defects of Q2 are rejected through this design.

Ids: G given facts, D decisions, M modules, U uses edges, I interfaces, Q questions. Marks: GIVEN (source) · DECIDED (architect, date) · PROPOSED · OPEN.

**Delegation.** Q1 says: "The design skill may determine the abstraction and module boundaries." Q3 says: "Hand that architectural seam to the design skill, then implement." The entries below are therefore PROPOSED and are implemented under that delegation. The questions at the end are the points where the architect may want to overrule the design. None of them blocks implementation unless the architect says so.

**Change scenarios**

| Change | Modules touched | Mark |
|---|---|---|
| A new schema v3 with a new composite profile | M1 (new variants; every `match` on `Schema` and `Profile` becomes a compile error until it is handled, FORCED); M2 (a new `composite_v3` sub-module); M4 (the new profile's text and the D6 dispatch, FORCED by the `match`) | PROPOSED |
| A new `System` member in a new composite version | M2's sub-module for that version only, then M4 emits it through M2. Validation, packets and conformance follow without an edit | PROPOSED |
| A schema v3 adds a model field | M1 `Feature` (new variant), plus the validate gate that maps a `Feature` to its diagnostic. Older schemas reject the field through `Schema::admits` | PROPOSED |
| Fixing a frozen profile's naming | Not allowed (G4). A fix is a new version. Q2's rejection rules are the one exception, and they reject inputs; they do not rename | GIVEN (G3, G4) |

The spread is accepted in two cases. Diagnostic codes and messages stay in `l2r_validate`, because they are validation's vocabulary. The text of each file stays in `l2r_plan`.

## Interfaces

### I1: M1 `l2r_model::profile`

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub enum Schema { V0, V1, V2 }

#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub enum Profile { TransitionCoreV0, CompositeV0, CompositeV1, TransitionCoreV1, CompositeV2 }

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Kind { Machine, Composite }

/// A model field that only some schemas admit.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Feature { Ports, MailboxCapacity, PortDirection, PortCapacity }

impl Schema {
    pub const ALL: [Schema; 3];
    pub fn parse(id: &str) -> Option<Schema>;   // the one place a schema string is compared
    pub fn id(self) -> &'static str;            // "l2r.architecture/v0" …: the bytes of today's constants
    pub fn admits(self, profile: Profile) -> bool;
    pub fn admits_feature(self, feature: Feature) -> bool;
}

impl Profile {
    pub const ALL: [Profile; 5];
    pub fn parse(id: &str) -> Option<Profile>;  // the one place a profile string is compared
    pub fn id(self) -> &'static str;
    pub fn kind(self) -> Kind;
    pub fn schema(self) -> Schema;                      // the schema that introduced it
    pub fn admits_child(self, child: Profile) -> bool;  // composite/v1: transition-core/v0 only
}

impl Model { pub fn parsed_schema(&self) -> Option<Schema>; pub fn features(&self) -> Vec<Feature>; }
impl Component { pub fn parsed_profile(&self) -> Option<Profile>; pub fn kind(&self) -> Option<Kind>; }
impl Port { pub fn features(&self) -> Vec<Feature>; }
```

As implemented (step 2a):
- `must_be_root` was dropped. Its one use sits inside the `composite/v1` arm, where it was a tautology.
- The model reports which gated features it uses, and the schema says which it admits. The S015 gates now ask both.
- After the independent review:
  - Every decision by schema or profile is an exhaustive `match`, or names the admitted schemas explicitly. That covers validate's dispatch, `Schema::admits`, S019, the profile-shape rules, `render`, packets and the Lean network tail.
  - `admits_child` is correct for every profile.
  - Classification within `v2` asks `kind()` among the profiles `v2` admits.
  - The planner reads profiles from `Validated`.
- Deliberately kept: rules of the frozen `v0`/`v1` profiles name their exact profile, for example M003 "only `transition-core/v0` sends" and the `composite/v0` planner's machine test. The rule belongs to that version, not to the kind.

- **Guarantees carried by types:** after parsing, a schema or profile is one of a closed set. Every classification is an exhaustive `match`, so a new variant is a compile error at each site that must decide about it (`liskov-zilles-1974-abstract-data-types`, Interpretation 1). Each string is compared once, in `parse`. That is the opposite of a registry of string comparisons (G1).
- **Obligations the signatures do not show:**
  - `id(parse(s)?) == s` for every supported string, tested over `ALL`.
  - The answers reproduce today's acceptance exactly. The only new rejections are those of Q2. Tested by the existing rule tests and by the examples.
- **Representation (Alternatives):**
  - **A, PROPOSED.** `Model.schema` and `Component.profile` stay `String` in the serde types. `l2r_validate` parses them once, and `Validated` carries the typed values (I3).
    - Canonical JSON is unchanged by construction (G6).
    - Unknown strings are still reported as S001/S007 findings among the other findings (G8).
    - The cost: code that reads `Model` without `Validated` sees strings. That is today's CLI `report` (`render` runs on invalid models); it parses too.
  - **B.** The serde fields become `Schema` and `Profile`, serialized under the same strings.
    - Canonical JSON is also unchanged.
    - But an unknown profile becomes a TOML parse error. It is then reported alone, before any other finding, which changes the diagnostics of invalid models (G8).
  - Caller knowledge: the same for both. Calls per intent: one `parse` under A, none under B.
  - Recommendation: **A**. It keeps the diagnostics, and therefore the documented rule codes, unchanged.

Mark: PROPOSED

### I2: M2 `l2r_model::rust_names`

```rust
/// `request_latch` → `RequestLatch`. Frozen: every profile version's output depends
/// on it (G4), so it is byte-for-byte today's `l2r_plan::text::type_name`.
pub fn type_name(identifier: &str) -> String;
/// `type_name`, when that is a usable Rust type name (today's `names::upper_camel`).
pub fn rust_type_name(identifier: &str) -> Option<String>;

/// Two things the architect named apart that would meet as one name in generated code.
pub enum Namespace { Field, Method, Type, Variant, RouteFunction, Module }
pub enum Owner { Component(String), Port(String), Edge(String), LeanType(String), Profile, Std }
pub enum Problem {
    Conflict { namespace: Namespace, name: String, first: Owner, second: Owner },
    NotARustName { namespace: Namespace, name: String, owner: Owner },
}

pub mod composite_v0 {
    pub struct Child<'a> { pub id: &'a str, pub module: &'a str, pub is_machine: bool }
    pub struct SystemNames { /* private */ }
    impl SystemNames {
        /// Every name the composite/v0 module of these children generates;
        /// `Err` lists every conflict, not only the first.
        pub fn new(children: &[Child<'_>], edges: &[&str]) -> Result<SystemNames, Vec<Problem>>;
        pub fn state_field(&self, module: &str) -> &str;     // "{m}"
        pub fn inbox_field(&self, module: &str) -> &str;     // "{m}_inbox"
        pub fn route_from(&self, module: &str) -> &str;      // "route_from_{m}"
        pub fn envelope_variant(&self, id: &str) -> &str;    // type_name(id)
        pub fn edge_function<'a>(&self, edge: &'a str) -> &'a str;  // the edge id
        pub fn fields(&self) -> &[String];  // and methods(), types(), route_functions()
    }
    pub const FIELDS: &[&str];   // "next"
    pub const METHODS: &[&str];  // "CHILDREN", "deliver", "is_settled", "new", "run", "send", "step_once"
    pub const TYPES: &[&str];    // "Envelope", "System", "Unsettled", "VecDeque"
    pub const STD_MODULES: &[&str]; // "std": `use std::collections::VecDeque`
}
pub mod composite_v1 { /* the same shape for G10: inbox types, send_{port}, attempt_{m},
                          message_type(port), capacity_const(child), route functions {edge} / port_{port};
                          STD_TYPES = "Default", "Option", "Result" (named unqualified by the template) */ }
pub mod composite_v2 { /* the names S020, packet.rs and recorder.rs restate today (G11):
                          {id}_state, {id}_inbox, {id}_outbox, send_{id}, take_{id}, attempt_{id},
                          the type prefixes, and hop_function_name */ }
```

- **Guarantees carried by types:** a `SystemNames` exists only for a set of names without conflicts (`liskov-zilles-1974-abstract-data-types`, Interpretation 1).
  - Validation constructs one per composite and keeps it in `Validated` (I3).
  - The planner takes its names from there and never rebuilds them, so the checked set and the emitted set are one value (05e855e).
- **Fixed names** (`next`, `run`, `System`, …) are written in the planner's literal text and listed once in `FIELDS`, `METHODS` and `TYPES`. Putting each one through a constant would make the frozen templates unreadable. Their agreement is TESTED, not FORCED: `l2r_plan_generated_names_test` reads the planned files back and requires exactly the listed names.
- **Q2 through I2:**
  - Defect 1 is a `composite_v0` or `composite_v1` conflict, a field `next` against a child module `next`.
  - Defect 2 is a `composite_v1` conflict, two distinct Lean names giving one `message_type`. The same Lean name on two ports is one type and no conflict.
  - Its family (MEASURED with `preview` after the decision): a last segment that is not a usable type name (`Timer'`, `Self`), or one named like a generated type (`System`, `<Child>Inbox`).
  - Found by the independent review: a type that would hide a standard name the template uses (`Option`, `Result`, `Default`), and in v0 a child module `std`. Standard names are claimed with owner `Std` and are not listed as declared names.
  - The rules cover names only. Other causes of a compile error in generated code are not checked by them.
  - Both are rejected in validation with new codes: S021 for `System` and module names in v0/v1, P005 for port message types. v2 keeps S020 and its messages.
- **Obligations the signatures do not show:**
  - Each accessor returns exactly the bytes the planner writes today. This is checked by the pins, the examples' drift tests and a differential corpus run at the PR (I4).
  - The accessors panic on an unknown module or id, which validation has excluded. That is the planner's existing panic policy (F14).
- **Depth:** the caller passes the children once and asks by name. The scheme, the case conversion and the conflict search stay hidden.
- **Alternatives:**
  - **A, PROPOSED.** A conflict-free `SystemNames` value per version, as above.
  - **B.** Free functions per member (`inbox_field(m) -> String`), plus a `members(...)` enumeration that validation checks.
    - B needs no value threaded through the planner.
    - But nothing forces the planner to use the functions. An inline `"next"` would bypass them, and only tests would catch it.
    - A carries the guarantee in a type; B leaves it as an obligation.
  - Recommendation: **A**.
- **Placement (Alternatives):**
  - **A, PROPOSED.** A module of `l2r_model`.
  - **B.** A new crate `l2r_names` between `l2r_model` and `l2r_validate`.
  - Under A the names are part of what a profile is: its published Rust interface, which work packets hand to implementers (G2). That matches "in the domain model" (G1), and no crate is added.
  - B separates the domain model from output vocabulary and lets Bazel visibility enforce who may use it.
  - Recommendation: **A**. It is one decision with a single owner either way; see Q-A.

Mark: PROPOSED

### I4: compatibility protection (G1, G4)

At each implementing PR:
1. The existing pins, fixtures and example drift tests (`l2r_check_test`) pass unchanged.
2. **A differential run.** A corpus of valid models (the examples, plus generated variations: every v0/v1/v2 profile, nested v0 composites, several ports and edges, unusual ids) is planned by `main`'s `l2r` and by the branch's. The plan digest and every file's bytes must be equal. Models that the new rules reject are listed separately; they must be exactly the Q2 cases.
3. The approval of every example stays current (`l2r check`).

The differential run is evidence for the PR. It is not the immutability guarantee (G4). The guarantee is structural: each frozen version has its own `rust_names` sub-module and its own planner module, and both are changed only by Q2's rejections.

Mark: PROPOSED
