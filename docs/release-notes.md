# Release notes

## 0.1.0 (experimental)

The first release. *Experimental* means: the workflow is complete and
reproducible and every claim below is checked in CI, but the model schemas,
the generated API and the command line may still change between releases, and
the newest profiles are tested against Lean rather than proved (see "Proved,
tested, assumed").

### What you can do with it

Start a system of your own in a repository of your own, following
[`getting-started.md`](getting-started.md):

1. `l2r init` creates a valid project: architecture model, Lean specification,
   exported inventory, a Bazel workspace that uses L2R as a dependency, and a
   Lake package for evidence about the composed system.
2. You specify behaviour in Lean and export what Lean elaborated
   (`l2r inventory`).
3. You describe the architecture: components, nesting, state ownership, typed
   ports, message edges, capacities (`l2r validate`, `l2r render`).
4. You review exactly what would be written and approve that plan
   (`l2r preview`, `l2r approve`); only then does `l2r generate` write.
5. An implementer or coding agent fills in the implementation files, which L2R
   never overwrites (`l2r packet` is the work packet). A drift test
   (`l2r_check_test`) fails when the model, the Lean inventory, the approval and
   the generated files stop agreeing.
6. `l2r lean-composition` and `l2r conformance` derive the Lean network your
   model approves and a harness that compares the generated scheduler, with
   your implementation, against Lean.

`tools/e2e/new_project.sh` runs all of this in CI in a fresh workspace outside
this repository, with the pinned Lean, including the inventory export and the
conformance replay, and checks every refusal on the way.

### Using it

L2R is used as a Bazel module, pinned to a commit. `l2r init <dir> --id <id>
--workspace-commit <commit>` writes the `MODULE.bazel` for you; it contains:

```starlark
bazel_dep(name = "l2r", version = "0.1.0")
git_override(
    module_name = "l2r",
    remote = "https://github.com/syncom-systems/l2r.git",
    commit = "<the commit of this release>",
)
```

Supported hosts: Linux x86_64 and macOS arm64 (the pinned Lean and the proof
lane exist for those two). Bazel is the only build interface; there is no Cargo
build and no published crate.

### Profiles and schemas in this release

Profiles and schemas are immutable: a change in generated bytes is a new
version, and the older ones keep producing what they produced.

| Model schema | Profiles | Adds |
| --- | --- | --- |
| `l2r.architecture/v0` | `transition-core/v0`, `composite/v0`, `crate-root/v0` | pure state machines, asynchronous composition with per-child mailboxes |
| `l2r.architecture/v1` | `composite/v1` | mailbox capacities with backpressure, typed input ports, `Blocked` instead of a silent stall |
| `l2r.architecture/v2` | `transition-core/v1`, `composite/v2`, `crate-root/v1` | nested composites behind typed ports, output ports as bounded outboxes, data-carrying states and messages |

Decisions: [ADR-0001 to ADR-0005](https://github.com/syncom-systems/l2r/discussions/categories/adrs),
all accepted.

### Proved, tested, assumed

These are different kinds of evidence and L2R never presents one as another.
[`verification.md`](verification.md) defines them; this is the summary for this
release.

**Proved in Lean, re-checked in CI** (audited for axioms, statements pinned,
seeded defects and proof bypasses must be rejected):

- The Rust transition functions and message routes of `examples/crossing`
  (schema `v0`) and `examples/crossing_v1` (schema `v1`) refine their Lean
  specifications: the committed Rust is re-extracted with Charon and Aeneas and
  the refinement is proved.
- For `examples/crossing_v1`, the generated `composite/v1` scheduler itself is
  proved to refine its Lean model (for that example; the technique does not yet
  scale to larger networks).
- System properties over every permitted interleaving, for the Lean networks
  derived from the approved models: a safety invariant for `crossing`; safety,
  capacity, deadlock-freedom and non-stranding for `crossing_v1`; the valve
  interlock for `tank_station`. Each is carried over to the Lean *model* of the
  generated scheduler.
- The Lean scheduler models only take steps the semantics permits
  (`lean/L2R/Async.lean`, `Async1.lean`, `Async1Ports.lean`).

**Tested, not proved:**

- **`composite/v2` and `transition-core/v1` (schema `v2`).** The generated
  scheduler, together with the handwritten implementations of data-carrying
  machines, is compared with the Lean scheduler model over the Lean `step`
  functions by bounded conformance testing: every operation sequence up to a
  fixed length plus seeded random sequences, comparing every result, machine
  state, mailbox and outbox after every operation (`l2r conformance`). **There
  is no proof that the `v2` scheduler or any data-carrying machine
  implementation refines its Lean specification.** A defect outside the tested
  sequences would not be found.
- The `composite/v0` scheduler is tied to its Lean model by conformance testing
  only.
- Contract tests generated for each machine are tests.

**Assumed, and stated where it is used:**

- The system theorems constrain the environment (for example, that it takes
  from the outboxes); the generated API does not enforce those assumptions.
- Liveness for `crossing_v1` holds under weak fairness of deliveries and a
  timer that is accepted again and again. That the round-robin scheduler
  provides weak fairness is assumed, not proved.
- The Lean kernel, Charon, Aeneas and the Rust compiler are trusted. mathlib's
  compiled libraries are trusted inputs to the Aeneas lane and are not
  hash-pinned.
- The approval record says a plan was reviewed; it does not authenticate who
  reviewed it ([`governance.md`](governance.md)).

### Limits

- Schema `v2` data types are a closed subset: non-recursive structures and
  inductives over `Bool`, `UInt8/16/32/64`, `Option` and other such types. No
  `Nat`, `Int`, strings or collections.
- An input port has one target. Capacities are at most 64; an output has at
  most 32 receivers.
- For `tank_station` only the interlock safety property is proved: no liveness
  property, and `Blocked` is reachable by design when the environment does not
  take from an outbox.
- No graphical editor and no state-space exploration; the views are the CLI
  preview and the Mermaid rendering.
- No signing and no identity system.
